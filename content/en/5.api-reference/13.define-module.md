## Overview

`defineModule` declares a self-contained feature module — its config schema, lifecycle hooks, and public API. Modules live in `src/modules/<name>/index.ts` (or `src/modules/<name>.ts`), or are installed as npm packages listed in the [`modules` config key](/api-reference/define-glyria-config#modules).

```ts
// src/modules/economy/index.ts
export default defineModule({
  name: "economy",
  version: "1.0.0",
  description: "Balances and daily rewards",
  defaultConfig: { startingBalance: 100 },

  setup(ctx) {
    // returned object = the module's public API
    return {
      async addBalance(userId: string, amount: number) {
        const current = (await ctx.store.get<number>(`bal:${userId}`)) ?? 0
        await ctx.store.set(`bal:${userId}`, current + amount)
      },
    }
  },

  hooks: {
    onReady(ctx) {
      ctx.logger.info("economy ready")
    },
  },
})
```

::tip{title="Auto-import"}
`defineModule`, `defineCommand`, `defineEvent`, and `defineHook` are available globally — no import needed.
::

## ModuleDefinition

| Key             | Type                              | Required | Description                                                              |
| --------------- | --------------------------------- | -------- | ------------------------------------------------------------------------ |
| `name`          | `string`                          | ✅       | Unique module name (`defineModule` throws without it)                    |
| `version`       | `string`                          | —        | Informational version, shown by `glyria module list`                     |
| `description`   | `string`                          | —        | Informational description                                                |
| `dependsOn`     | `string[]`                        | —        | Names of modules that must load before this one                          |
| `config`        | `ConfigSchema<C>`                 | —        | Validates the module's entry in `moduleConfig` (zod schemas work as-is)  |
| `defaultConfig` | `unknown`                         | —        | Used when `moduleConfig` has no entry for this module                    |
| `setup(ctx)`    | `(ctx: ModuleContext<C>) => unknown` | —     | Entry point — its return value is the module's **public API**, consumable via `ctx.modules.get(name)` |
| `hooks`         | `ModuleHooks<C>`                  | —        | Lifecycle and command hooks                                              |

### `config` — schema validation

`ConfigSchema<C>` is zod-compatible — anything with a `.parse()` method, or a plain validation function:

```ts
type ConfigSchema<C> = { parse(input: unknown): C } | ((input: unknown) => C)
```

```ts
import { z } from "zod"

export default defineModule({
  name: "economy",
  config: z.object({
    startingBalance: z.number().default(100),
    currency: z.string().default("🪙"),
  }),
  setup(ctx) {
    ctx.config.startingBalance // typed number
  },
})
```

The raw input is `moduleConfig[name]` from `glyria.config.ts`, falling back to `defaultConfig`. A schema that throws disables the module (`invalid config` status) without taking the bot down.

## ModuleContext

Passed to `setup()` and every lifecycle hook.

| Member    | Type                   | Description                                                            |
| --------- | ---------------------- | ----------------------------------------------------------------------- |
| `name`    | `string`               | The module's name                                                       |
| `client`  | `GlyriaClient`         | The bot client                                                          |
| `config`  | `C`                    | Validated config for this module (from `moduleConfig`)                  |
| `store`   | `ScopedStore`          | Store scoped to this module (`module:<name>:` prefix)                   |
| `logger`  | `ModuleLogger`         | `info`/`warn`/`error`, tagged `mod:<name>` in the console               |
| `modules` | `ModuleRegistryAccess` | Access other modules' public APIs: `get(name)` (throws when the target is not loaded or inactive) and `has(name)` |

```ts
setup(ctx) {
  const economy = ctx.modules.get("economy") // typed via GlyriaModules augmentation
  ctx.logger.info(`loaded, depends on economy: ${ctx.modules.has("economy")}`)
}
```

## ModuleHooks

All hooks may be async. Every hook is wrapped in try/catch by the manager — a crashing hook is logged, reported to `onError`, and counted (see [isolation rules](#isolation-rules)).

| Hook                                | Signature                                                             | Fires                                                    |
| ----------------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------- |
| `onLoad`                            | `(ctx: ModuleContext<C>) => unknown`                                    | Before `setup()`, when the module loads                   |
| `onReady`                           | `(ctx: ModuleContext<C>) => unknown`                                    | When the bot is ready                                     |
| `onUnload`                          | `(ctx: ModuleContext<C>) => unknown`                                    | Before hot reload / hot-swap / shutdown                   |
| `onError`                           | `(ctx: ModuleContext<C>, error: unknown) => unknown`                    | When the module (or any of its hooks) throws              |
| `onGuildJoin`                       | `(ctx: ModuleContext<C>, guild) => unknown`                             | On `guildCreate`                                          |
| `onGuildLeave`                      | `(ctx: ModuleContext<C>, guild) => unknown`                             | On `guildDelete`                                          |
| `beforeCommand`                     | `(ctx: GlyriaContext, meta: CommandRunMeta, next: () => Promise<void>) => unknown` | Global middleware — before **every** command. Skip `next()` to cancel |
| `afterCommand`                      | `(ctx: GlyriaContext, meta: CommandRunMeta, result: unknown) => unknown` | After every command handler completes                     |
| `onCommandRun`                      | `(ctx: GlyriaContext, meta: CommandRunMeta) => unknown`                 | Notification when a command runs                          |

### CommandRunMeta

| Field  | Type                              | Description                                        |
| ------ | --------------------------------- | -------------------------------------------------- |
| `name` | `string`                          | Fully-resolved command key, e.g. `"config:theme:set"` |
| `kind` | `"chat" \| "user" \| "message"`   | Which command surface was invoked                  |

### `beforeCommand` middleware

`beforeCommand` hooks across all active modules form a Koa-style chain. Call `next()` to let the pipeline continue; not calling it cancels the command silently (your hook is expected to have replied already). A middleware that throws does **not** block other commands — the chain continues past it.

```ts
hooks: {
  async beforeCommand(ctx, meta, next) {
    const banned = await ctx.g.store.user.get<boolean>("blacklisted")
    if (banned) {
      await ctx.g.reply.error("You are blacklisted.").ephemeral()
      return // no next() → command cancelled
    }
    await next()
  },
}
```

## SDK helpers

Thin, typed entry points for module authors — the same builders, stricter intent:

| Helper                   | Returns          | Description                                       |
| ------------------------ | ---------------- | ------------------------------------------------- |
| `defineCommand(fn)`      | `GlyriaCommand`  | `fn` receives a fresh `GlyriaCommand`             |
| `defineEvent(fn)`        | `GlyriaEvent`    | `fn` receives a fresh `GlyriaEvent`               |
| `defineHook(hooks)`      | `ModuleHooks<C>` | Identity helper for typing a standalone hooks object |

```ts
// src/modules/economy/commands/balance.ts
export default defineCommand((cmd) =>
  cmd
    .setName("balance")
    .setDescription("Show your balance")
    .execute(async (ctx) => {
      const bal = (await ctx.g.store.user.get<number>("balance")) ?? 0
      await ctx.g.reply.primary(`You have ${bal} 🪙`)
    }),
)
```

## Typed inter-module APIs

Augment the `GlyriaModules` interface to make `ctx.modules.get(name)` return a typed API:

```ts
declare module "@glyria/bot" {
  interface GlyriaModules {
    economy: { addBalance(userId: string, amount: number): Promise<void> }
  }
}

// elsewhere, in another module:
const economy = ctx.modules.get("economy")
await economy.addBalance(userId, 50) // fully typed
```

## ModuleManager

The framework instantiates one `ModuleManager`; you interact with it mostly through the CLI (`glyria module list`, `glyria module reload <name>`). Public methods:

| Method                          | Returns            | Description                                                       |
| ------------------------------- | ------------------ | ------------------------------------------------------------------ |
| `register(definition, source?)` | `boolean`          | Queue a module definition (`false` when the value is not a `defineModule` result) |
| `loadAll(moduleConfig?)`        | `Promise<void>`    | Topologically sort by `dependsOn`, then load each module (validate config → `onLoad` → `setup`) |
| `reload(name, moduleConfig?)`   | `Promise<boolean>` | Hot-swap a single module in place — `onUnload`, re-import from its source, reload. Others untouched |
| `hotReload(moduleConfig?)`      | `Promise<void>`    | Unload everything, re-discover from disk, reload all               |
| `list()`                        | `{ name, version?, status, reason?, hooks }[]` | Introspection snapshot of every module         |
| `getApi(name)`                  | `unknown`          | The public API returned by a module's `setup()`                    |

### Load order

`dependsOn` drives a topological sort. A module fails to load (status `error`) when:

- a dependency is missing — `missing dependency "<dep>"`
- a dependency itself failed — `dependency "<dep>" failed to load`
- a dependency cycle exists — `dependency cycle: a → b → a`

### Isolation rules

A crashing module must never take the bot down:

- Config validation, `onLoad`, and `setup` failures disable **that module only** (status `error`, reason `invalid config` / `setup crashed`).
- Every runtime hook runs in try/catch; an error is logged, forwarded to the module's `onError` hook (which is itself allowed to fail silently), and counted.
- After **5** hook errors over the module's lifetime (the counter is cumulative and never resets) the module is auto-disabled (status `disabled`, reason `auto-disabled after 5 hook errors`).
- A throwing `beforeCommand` middleware does not block the pipeline — the chain continues with the next module.

### ModuleStatus

| Status     | Meaning                                                     |
| ---------- | ------------------------------------------------------------ |
| `active`   | Loaded and running — hooks fire, API available               |
| `disabled` | Auto-disabled after too many hook errors                     |
| `error`    | Failed to load (bad config, crashed setup, dependency issue) |
