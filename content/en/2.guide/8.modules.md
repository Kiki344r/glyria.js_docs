## Overview

A module is a self-contained feature: a manifest plus optional `commands/`, `events/` and `components/` folders, all auto-loaded. Modules get their own scoped store and logger, lifecycle hooks, global command middleware, dependency resolution and crash isolation.

Modules come in two flavors:

| Flavor | Location | Manifest |
|---|---|---|
| Local | `src/modules/<name>/` | `index.ts` (or a single `src/modules/<name>.ts` file) |
| npm package | `node_modules/<pkg>` declared in `modules: []` | `glyria.module.ts` or `index.ts` |

```text
src/modules/economy/
  index.ts        # manifest (defineModule)
  commands/       # auto-loaded like src/commands/
    balance.ts
  events/         # auto-loaded like src/events/
  components/     # auto-loaded like src/components/
```

## Defining a module

```ts
// src/modules/economy/index.ts
export default defineModule({
  name: "economy",
  version: "1.0.0",
  description: "Currency and balances",

  setup(ctx) {
    ctx.logger.info("economy loaded")

    // the returned object is the module's public API
    return {
      addBalance: async (userId: string, amount: number) => {
        const current = (await ctx.store.get<number>(`balance:${userId}`)) ?? 0
        await ctx.store.set(`balance:${userId}`, current + amount)
      },
    }
  },

  hooks: {
    onReady(ctx) {
      ctx.logger.info("bot is ready")
    },
  },
})
```

::tip{title="Auto-import"}
`defineModule` — along with `defineCommand`, `defineEvent` and `defineHook` — is available globally.
::

| Field | Description |
|---|---|
| `name` | Required, unique module name |
| `version` / `description` | Metadata, shown by `glyria module list` |
| `dependsOn` | Names of modules that must load first |
| `config` | Validation schema for this module's config entry |
| `defaultConfig` | Used when no config entry is provided |
| `setup(ctx)` | Entry point — returns the module's public API |
| `hooks` | Lifecycle hooks and command middleware |

## Module context

Every hook and `setup()` receives a `ModuleContext`:

| Property | Description |
|---|---|
| `ctx.name` | The module's name |
| `ctx.client` | The `GlyriaClient` |
| `ctx.config` | Validated config from `moduleConfig` |
| `ctx.store` | [Store](/guide/store) scoped to `module:<name>:` — automatic, no prefixing |
| `ctx.logger` | `info` / `warn` / `error`, prefixed with `mod:<name>` |
| `ctx.modules` | Access other modules' public APIs |

## Lifecycle hooks

```ts
hooks: {
  onLoad(ctx) {},                    // before setup()
  onReady(ctx) {},                   // bot logged in and ready
  onUnload(ctx) {},                  // shutdown or reload
  onCommandRun(ctx, meta) {},        // every command invocation (observer)
  onError(ctx, error) {},            // any error surfaced to the module system
  onGuildJoin(ctx, guild) {},        // bot added to a guild
  onGuildLeave(ctx, guild) {},       // bot removed from a guild
}
```

`meta` is `{ name, kind }` — the fully-resolved command key (e.g. `"config:theme:set"`) and the command kind (`"chat"`, `"user"`, `"message"`).

## Command middleware

`beforeCommand` runs before **every** command of the bot, koa-style: call `next()` to continue the chain, skip it to cancel the command silently (your module has presumably already replied). `afterCommand` runs after the handler completes, with its return value.

```ts
// src/modules/anti-spam/index.ts
export default defineModule({
  name: "anti-spam",

  hooks: {
    async beforeCommand(ctx, meta, next) {
      // ctx.g.store.user is already scoped to the invoking user
      const last = (await ctx.g.store.user.get<number>("lastCommand")) ?? 0

      if (Date.now() - last < 1_000) {
        await ctx.g.reply.warning("Slow down!", { ephemeral: true })
        return // next() not called → command cancelled
      }

      await ctx.g.store.user.set("lastCommand", Date.now())
      await next()
    },

    async afterCommand(ctx, meta, result) {
      console.log(`${meta.name} finished`)
    },
  },
})
```

Middleware receives the same wrapped context as command handlers — `ctx.g` works everywhere. A middleware that throws does **not** block other commands: the chain continues past it, and the error counts toward the module's error budget.

## Dependencies

Declare load-order dependencies with `dependsOn` — modules are topologically sorted before loading:

```ts
export default defineModule({
  name: "shop",
  dependsOn: ["economy"],
  // ...
})
```

A **missing dependency** or a **dependency cycle** doesn't crash the bot: the affected module is marked `error` with a clear reason (`missing dependency "economy"`, `dependency cycle: shop → economy → shop`) and everything else loads normally.

## Per-module config

Users configure modules in `glyria.config.ts` under `moduleConfig`, keyed by module name:

```ts
// glyria.config.ts
export default defineGlyriaConfig({
  modules: ["@acme/economy"],
  moduleConfig: {
    economy: { currency: "🪙", dailyAmount: 100 },
  },
})
```

The module validates its entry with any zod-compatible schema (anything exposing `.parse()`, or a plain validation function):

```ts
import { z } from "zod"

const schema = z.object({
  currency: z.string().default("$"),
  dailyAmount: z.number().int().positive(),
})

export default defineModule({
  name: "economy",
  config: schema,
  setup(ctx) {
    ctx.config.dailyAmount // typed via the schema
  },
})
```

Invalid config disables the module at startup with an explicit error — the bot keeps running.

## Crash isolation

A broken module must never take the bot down:

- Every hook call is try/caught; errors are logged and forwarded to the module's `onError`.
- After **5 consecutive hook errors**, the module is auto-disabled.
- A crashing `setup()` marks the module `error` immediately.

| Status | Meaning |
|---|---|
| `active` | Loaded and running |
| `disabled` | Auto-disabled after too many hook errors |
| `error` | Failed to load (bad config, missing dependency, setup crash) |

## Inter-module APIs

The object returned by `setup()` is the module's public API. Other modules consume it via `ctx.modules`:

```ts
export default defineModule({
  name: "shop",
  dependsOn: ["economy"],

  setup(ctx) {
    const economy = ctx.modules.get("economy")
    // ctx.modules.has("economy") → boolean
  },
})
```

`get()` throws if the target module isn't loaded and active. To make it **typed**, augment the `GlyriaModules` interface:

```ts
// src/modules/economy/index.ts
declare module "@glyria/bot" {
  interface GlyriaModules {
    economy: {
      addBalance(userId: string, amount: number): Promise<void>
    }
  }
}
```

Now `ctx.modules.get("economy")` returns the declared API type everywhere.

## Hot-swap

Reload a single module in place — `onUnload` runs, the file is re-imported, hooks are re-registered, other modules are untouched:

```ts
await client.modulesManager.reload("economy")
```

In dev (`glyria dev`), the watcher hot-reloads modules automatically on save. In production, `glyria reload` swaps everything with [zero downtime](/guide/production).

## Testing

`createTestContext()` (auto-imported) builds a fake interaction wrapped in a full glyria context — run handlers and middleware without Discord, then assert on what was sent:

```ts
// test/economy.test.ts
import { describe, it, expect } from "vitest"
import balance from "../src/modules/economy/commands/balance.js"

describe("balance", () => {
  it("replies with the user's balance", async () => {
    const ctx = createTestContext({ userId: "42", guildId: "guild-1" })

    const [handler] = balance.getHandlers()
    await handler.handler(ctx as never)

    expect(ctx.repliesText()).toEqual(["✅ Your balance: 0 🪙"])
  })
})
```

`ctx.replies` holds every captured send (`via`, `payload`, `timestamp`); `ctx.repliesText()` extracts the plain text from the Embed V2 payloads. Slash option values and subcommand paths can be faked with the `options` and `subcommand` fields of `createTestContext`.

## CLI

```bash
glyria module create economy   # scaffold src/modules/economy (manifest + example command)
glyria module list             # discovered modules with version, deps and hooks
```

## Publishing to npm

A module package is a normal npm package: put `defineModule(...)` in `glyria.module.ts` (or `index.ts`) at the package root, ship `commands/` / `events/` / `components/` folders alongside it, and run `npm publish`. Consumers install it and add the package name to their config:

```ts
// glyria.config.ts
export default defineGlyriaConfig({
  modules: ["@acme/economy"],
})
```

That's it — glyria discovers the manifest and the folders automatically at startup.
