## Overview

Running a glyria bot in production is two commands:

```bash
glyria build   # compile to dist/
glyria start   # run under the self-healing supervisor
```

Deploying an update never restarts the process:

```bash
glyria build
glyria reload  # zero-downtime hot swap
```

## Zero-downtime deploys

`glyria reload` reads the running bot's pid from `.glyria/bot.pid` and sends it **SIGUSR2**. The bot then swaps commands, events, components and modules **in memory**:

- The gateway connection never drops — no missed interactions, no "bot offline" blip.
- The config is re-read, module `onUnload`/`onLoad` hooks run.
- Commands are only re-registered with Discord when the payload actually changed.

```bash
glyria build && glyria reload
```

::warning{title="Not supported on Windows"}
SIGUSR2 doesn't exist on Windows — `glyria reload` exits with an error there. Use a full restart instead.
::

::note{title="pid file"}
The bot writes its pid to `.glyria/bot.pid` at startup. If the file is missing, the bot isn't running (or was started outside `glyria start`/the built entry point).
::

## Self-healing supervisor

`glyria start` runs the built bot under a supervisor with crash recovery:

| Behavior | Detail |
|---|---|
| Backoff restarts | Crash → restart after 1s, 2s, 4s, ... (exponential) |
| Stable snapshot | After **60s** of uptime, the current `dist/` is snapshotted to `.glyria/last-good` |
| Crash-loop rollback | **3 crashes within 60s** → `dist/` is replaced by the last-good snapshot and the bot reboots on it |
| Give up | Crash loop while already on the stable build (or no snapshot) → exit |

So a bad deploy can't keep your bot down: it automatically falls back to the last build that ran stably for a minute.

## Deployment changelog

Configure a channel and glyria posts a changelog on every deployment that changes commands:

```ts
// glyria.config.ts
export default defineGlyriaConfig({
  changelog: {
    channel: "123456789012345678",
  },
})
```

On boot (and on reload), the registered command set is compared against the previous deployment's snapshot (`.glyria/commands.snapshot.json`) and a styled message lists **added**, **updated** and **removed** commands. Nothing is posted when nothing changed. The snapshot is refreshed on every deployment either way.

## Interaction recording

glyria can record every command run — options, subcommand path, every reply sent, any error — as JSON files under `.glyria/interactions/`:

```ts
// glyria.config.ts
export default defineGlyriaConfig({
  recording: true,
})
```

Recording is **always on in dev** (`glyria dev`) and opt-in in production via `recording: true`.

Recordings power the time-travel tooling:

```bash
glyria replay <id>   # re-run a recorded interaction against your current code
glyria bench         # benchmark handlers with recorded inputs
glyria studio        # browse recordings in a local UI
```

See the CLI pages for [`glyria replay`](/cli/replay), [`glyria bench`](/cli/bench) and [`glyria studio`](/cli/studio).

## Checklist

- `glyria build` then `glyria start` under your process manager of choice (systemd, Docker, ...).
- Deploy updates with `glyria build && glyria reload` — no restart, no downtime.
- Keep the `.glyria/` directory writable and persistent: it holds the pid file, the last-good snapshot, the command snapshot, the JSON store and recordings.
- Set `changelog.channel` and `logChannel` to see what your bot is doing from Discord.
