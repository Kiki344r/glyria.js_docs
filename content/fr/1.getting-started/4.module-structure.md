Un module Glyria est soit un **dossier local** dans `src/modules/`, soit un **package NPM standard** déclaré dans `glyria.config.ts`. Dans les deux cas, Glyria découvre et charge automatiquement son manifeste, ses commandes, ses events et ses composants.

```txt
@glyria/your-module/
  src/
    glyria.module.ts   ← manifeste (defineModule)
    commands/
    events/
    components/
    index.ts
  dist/
    glyria.module.js
    commands/
    events/
    components/
    index.js
  package.json
```

Les modules locaux suivent la même forme, sans le packaging :

```txt
src/modules/economy/
  index.ts             ← manifeste (defineModule)
  commands/
  events/
  components/
```

## Le manifeste

Le manifeste est l'identité du module : un export par défaut créé avec `defineModule()`. Pour les packages npm, Glyria cherche d'abord `glyria.module.ts`, puis se rabat sur `index.ts`.

```ts
// glyria.module.ts
export default defineModule({
  name: "timers",
  version: "1.0.0",
  dependsOn: [],

  setup(ctx) {
    // objet retourné = API publique, consommable via ctx.modules.get("timers")
    return { createJob, deleteJob }
  },
})
```

Voir le [guide du SDK de modules](/guide/modules) pour les hooks de cycle de vie, les middlewares, la validation de config et la résolution de dépendances.

## dist/ vs src/

En production, Glyria préfère la sortie de build : il cherche `dist/src/`, puis `dist/`, puis se rabat sur `src/`. En mode dev (`glyria dev`), `src/` l'emporte toujours lorsqu'il existe — même si `dist/` est également présent.

| Dossier              | Utilisé quand                                                  |
| -------------------- | -------------------------------------------------------------- |
| `src/`               | Mode dev (`glyria dev`), ou aucune sortie de build en production |
| `dist/src/`, `dist/` | Production, quand le package est build                          |

## commands/

Les commandes slash exposées par le module. Glyria analyse récursivement ce dossier et charge chaque fichier, exactement comme votre propre `src/commands/`.

```txt
dist/
  commands/
    ban.js
    kick.js
    config/
      logs.js
```

::tip{title="Sous-dossiers"}
Les sous-dossiers servent uniquement à l'organisation — chaque fichier, peu importe sa profondeur, est chargé comme une commande.
::

## events/

Les listeners d'événements Discord exposés par le module. Chargés aux côtés de votre propre `src/events/`.

## components/

Les handlers de composants typés ([boutons, selects, modals](/guide/components)) exposés par le module. Chargés aux côtés de votre propre `src/components/`.

## index.ts

Le point d'entrée principal du module. Tous les exports de ce fichier sont automatiquement disponibles dans le projet de l'utilisateur sous le namespace du module — aucun import nécessaire.

```ts
// @glyria/timers — src/index.ts
export const createJob = () => { ... }
export const deleteJob = () => { ... }
```

```ts
// Dans le projet de l'utilisateur — aucun import requis
const job = Timers.createJob(() => {
    console.log("runs every minute")
}, "* * * * *")
```

Le namespace est le nom du package sans son scope, débarrassé de ses caractères non alphanumériques, avec seulement la première lettre en majuscule — `@glyria/timers` → `Timers`, `@glyria/some-feature` → `Somefeature`.

::tip{title="Namespace vs ctx.modules"}
Le namespace global expose les **exports** du fichier globalement. La valeur de retour de `setup()` est une API distincte, vérifiée à l'exécution et consommée avec `ctx.modules.get("name")` — préférez-la pour les appels entre modules puisqu'elle respecte l'ordre de chargement et le statut des modules.
::

## package.json

Le champ `main` doit pointer vers votre point d'entrée build. Il est recommandé de déclarer `@glyria/bot` en peer dependency pour éviter d'embarquer plusieurs instances du framework dans le projet de l'utilisateur.

```json
{
  "name": "@glyria/your-module",
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "peerDependencies": {
    "@glyria/bot": "*"
  }
}
```

::tip{title="peerDependencies"}
Utiliser `peerDependencies` garantit que le module réutilise l'instance de `@glyria/bot` déjà installée dans le projet de l'utilisateur, plutôt que d'embarquer sa propre copie.
::

## Exemple minimal

Un module n'a pas besoin de tous les dossiers. Si un dossier n'existe pas, Glyria l'ignore silencieusement. Un module qui n'expose que des fonctions utilitaires via son `index.ts` est parfaitement valide.

```txt
@glyria/timers/
  dist/
    index.js    ← uniquement des exports, pas de commandes ni d'events
  package.json
```
