## Vue d'ensemble

Un module est une fonctionnalité autonome : un manifeste plus des dossiers optionnels `commands/`, `events/` et `components/`, tous chargés automatiquement. Les modules disposent de leur propre store et logger scopés, de hooks de cycle de vie, de middleware global de commandes, de résolution de dépendances et d'isolation des crashs.

Les modules existent en deux variantes :

| Variante | Emplacement | Manifeste |
|---|---|---|
| Local | `src/modules/<name>/` | `index.ts` (ou un simple fichier `src/modules/<name>.ts`) |
| Package npm | `node_modules/<pkg>` déclaré dans `modules: []` | `glyria.module.ts` ou `index.ts` |

```text
src/modules/economy/
  index.ts        # manifeste (defineModule)
  commands/       # chargé automatiquement comme src/commands/
    balance.ts
  events/         # chargé automatiquement comme src/events/
  components/     # chargé automatiquement comme src/components/
```

## Définir un module

```ts
// src/modules/economy/index.ts
export default defineModule({
  name: "economy",
  version: "1.0.0",
  description: "Currency and balances",

  setup(ctx) {
    ctx.logger.info("economy loaded")

    // l'objet retourné est l'API publique du module
    return {
      addBalance: async (userId: string, amount: number) => {
        const current = (await ctx.store.get<number>(`balance:${userId}`)) ?? 0
        await ctx.store.set(`balance:${userId}`, current + amount)
      },
    }
  },

  hooks: {
    onReady(ctx) {
      ctx.logger.info("bot is ready")
    },
  },
})
```

::tip{title="Auto-import"}
`defineModule` — ainsi que `defineCommand`, `defineEvent` et `defineHook` — est disponible globalement.
::

| Champ | Description |
|---|---|
| `name` | Requis, nom unique du module |
| `version` / `description` | Métadonnées — `version` est affichée par `glyria module list` |
| `dependsOn` | Noms des modules qui doivent se charger en premier |
| `config` | Schéma de validation pour l'entrée de config de ce module |
| `defaultConfig` | Utilisé quand aucune entrée de config n'est fournie |
| `setup(ctx)` | Point d'entrée — retourne l'API publique du module |
| `hooks` | Hooks de cycle de vie et middleware de commandes |

## Contexte de module

`setup()` et les hooks de cycle de vie reçoivent un `ModuleContext`. Les hooks du pipeline de commandes (`beforeCommand`, `afterCommand`, `onCommandRun`) reçoivent quant à eux le contexte de **commande** enveloppé — le même `ctx` (avec `ctx.g`) que celui des handlers de commandes.

| Propriété | Description |
|---|---|
| `ctx.name` | Le nom du module |
| `ctx.client` | Le `GlyriaClient` |
| `ctx.config` | Config validée depuis `moduleConfig` |
| `ctx.store` | [Store](/guide/store) scopé à `module:<name>:` — automatique, sans préfixage |
| `ctx.logger` | `info` / `warn` / `error`, préfixés avec `mod:<name>` |
| `ctx.modules` | Accès aux APIs publiques des autres modules |

## Hooks de cycle de vie

```ts
hooks: {
  onLoad(ctx) {},                    // avant setup()
  onReady(ctx) {},                   // bot connecté et prêt
  onUnload(ctx) {},                  // arrêt ou reload
  onCommandRun(ctx, meta) {},        // chaque invocation de commande (observateur)
  onError(ctx, error) {},            // toute erreur remontée au système de modules
  onGuildJoin(ctx, guild) {},        // bot ajouté à un serveur
  onGuildLeave(ctx, guild) {},       // bot retiré d'un serveur
}
```

`meta` est `{ name, kind }` — la clé de commande entièrement résolue (par exemple `"config:theme:set"`) et le type de commande (`"chat"`, `"user"`, `"message"`).

## Middleware de commandes

`beforeCommand` s'exécute avant **chaque** commande du bot, façon koa : appelez `next()` pour poursuivre la chaîne, omettez-le pour annuler la commande silencieusement (votre module a vraisemblablement déjà répondu). `afterCommand` s'exécute après la fin du handler, avec sa valeur de retour.

```ts
// src/modules/anti-spam/index.ts
export default defineModule({
  name: "anti-spam",

  hooks: {
    async beforeCommand(ctx, meta, next) {
      // ctx.g.store.user est déjà scopé à l'utilisateur invoquant
      const last = (await ctx.g.store.user.get<number>("lastCommand")) ?? 0

      if (Date.now() - last < 1_000) {
        await ctx.g.reply.warning("Slow down!", { ephemeral: true })
        return // next() non appelé → commande annulée
      }

      await ctx.g.store.user.set("lastCommand", Date.now())
      await next()
    },

    async afterCommand(ctx, meta, result) {
      console.log(`${meta.name} finished`)
    },
  },
})
```

Le middleware reçoit le même contexte enveloppé que les handlers de commandes — `ctx.g` fonctionne partout. Un middleware qui lève une erreur ne bloque **pas** les autres commandes : la chaîne continue au-delà, et l'erreur compte dans le budget d'erreurs du module.

## Dépendances

Déclarez des dépendances d'ordre de chargement avec `dependsOn` — les modules sont triés topologiquement avant le chargement :

```ts
export default defineModule({
  name: "shop",
  dependsOn: ["economy"],
  // ...
})
```

Une **dépendance manquante** ou un **cycle de dépendances** ne fait pas planter le bot : le module concerné est marqué `error` avec une raison claire (`missing dependency "economy"`, `dependency cycle: shop → economy → shop`) et tout le reste se charge normalement.

## Config par module

Les utilisateurs configurent les modules dans `glyria.config.ts` sous `moduleConfig`, indexé par nom de module :

```ts
// glyria.config.ts
export default defineGlyriaConfig({
  modules: ["@acme/economy"],
  moduleConfig: {
    economy: { currency: "🪙", dailyAmount: 100 },
  },
})
```

Le module valide son entrée avec n'importe quel schéma compatible zod (tout ce qui expose `.parse()`, ou une simple fonction de validation) :

```ts
import { z } from "zod"

const schema = z.object({
  currency: z.string().default("$"),
  dailyAmount: z.number().int().positive(),
})

export default defineModule({
  name: "economy",
  config: schema,
  setup(ctx) {
    ctx.config.dailyAmount // typé via le schéma
  },
})
```

Une config invalide désactive le module au démarrage avec une erreur explicite — le bot continue de tourner.

## Isolation des crashs

Un module cassé ne doit jamais faire tomber le bot :

- Chaque appel de hook est try/catché ; les erreurs sont loggées et transmises au `onError` du module.
- Après **5 erreurs de hooks** sur la durée de vie du module (le compteur ne se réinitialise jamais), le module est auto-désactivé.
- Un `setup()` qui plante marque immédiatement le module `error`.

| Statut | Signification |
|---|---|
| `active` | Chargé et en fonctionnement |
| `disabled` | Auto-désactivé après trop d'erreurs de hooks |
| `error` | Échec de chargement (config invalide, dépendance manquante, crash du setup) |

## APIs inter-modules

L'objet retourné par `setup()` est l'API publique du module. Les autres modules la consomment via `ctx.modules` :

```ts
export default defineModule({
  name: "shop",
  dependsOn: ["economy"],

  setup(ctx) {
    const economy = ctx.modules.get("economy")
    // ctx.modules.has("economy") → boolean
  },
})
```

`get()` lève une erreur si le module cible n'est pas chargé et actif. Pour la rendre **typée**, augmentez l'interface `GlyriaModules` :

```ts
// src/modules/economy/index.ts
declare module "@glyria/bot" {
  interface GlyriaModules {
    economy: {
      addBalance(userId: string, amount: number): Promise<void>
    }
  }
}
```

Désormais, `ctx.modules.get("economy")` retourne le type d'API déclaré partout.

## Hot-swap

Rechargez un module unique sur place — `onUnload` s'exécute, le fichier est ré-importé, les hooks sont ré-enregistrés, les autres modules ne sont pas touchés :

```ts
await client.modulesManager.reload("economy")
```

En dev (`glyria dev`), le watcher recharge à chaud les modules automatiquement à la sauvegarde. En production, `glyria reload` remplace le tout avec [zéro interruption](/guide/production).

## Tests

`createTestContext()` (auto-importé) construit une fausse interaction enveloppée dans un contexte glyria complet — exécutez handlers et middlewares sans Discord, puis vérifiez ce qui a été envoyé :

```ts
// test/economy.test.ts
import "@glyria/bot/globals" // installe les globales du runtime (GlyriaCommand, ...) sous vitest pur
import { describe, it, expect } from "vitest"
import { createTestContext } from "@glyria/bot"
import balance from "../src/modules/economy/commands/balance.js"

describe("balance", () => {
  it("replies with the user's balance", async () => {
    const ctx = createTestContext({ userId: "42", guildId: "guild-1" })

    const [handler] = balance.getHandlers()
    await handler.handler(ctx as never)

    expect(ctx.repliesText()).toEqual(["✅ Your balance: 0 🪙"])
  })
})
```

`ctx.replies` contient chaque envoi capturé (`via`, `payload`, `timestamp`) ; `ctx.repliesText()` extrait le texte brut des payloads Embed V2. Les valeurs d'options slash et les chemins de sous-commandes peuvent être simulés avec les champs `options` et `subcommand` de `createTestContext`.

## CLI

```bash
glyria module create economy   # génère src/modules/economy (manifeste + commande d'exemple)
glyria module list             # modules découverts avec version, dépendances et hooks
```

## Publier sur npm

Un package de module est un package npm normal : placez `defineModule(...)` dans `glyria.module.ts` (ou `index.ts`) dans le dossier `src/` du package — ou livrez-le build dans `dist/` — avec `commands/` / `events/` / `components/` à côté, et lancez `npm publish`. Glyria cherche le manifeste dans `dist/src/`, `dist/`, puis `src/` (pas à la racine nue du package) — voir [Structure d'un module](/getting-started/module-structure) pour le layout complet. Les consommateurs l'installent et ajoutent le nom du package à leur config :

```ts
// glyria.config.ts
export default defineGlyriaConfig({
  modules: ["@acme/economy"],
})
```

C'est tout — glyria découvre le manifeste et les dossiers automatiquement au démarrage.
