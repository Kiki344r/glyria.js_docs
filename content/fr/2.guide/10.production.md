## Vue d'ensemble

Faire tourner un bot glyria en production tient en deux commandes :

```bash
glyria build   # compile vers dist/
glyria start   # exécute sous le superviseur auto-réparant
```

Déployer une mise à jour ne redémarre jamais le processus :

```bash
glyria build
glyria reload  # hot swap sans interruption
```

## Déploiements sans interruption

`glyria reload` lit le pid du bot en cours d'exécution depuis `.glyria/bot.pid` et lui envoie **SIGUSR2**. Le bot remplace alors commandes, events, composants et modules **en mémoire** :

- La connexion à la gateway ne tombe jamais — aucune interaction manquée, aucun passage "bot hors ligne".
- La config est relue, les hooks `onUnload`/`onLoad` des modules s'exécutent.
- Les commandes ne sont ré-enregistrées auprès de Discord que si le payload a réellement changé.

```bash
glyria build && glyria reload
```

::warning{title="Non supporté sous Windows"}
SIGUSR2 n'existe pas sous Windows — `glyria reload` s'y termine avec une erreur. Utilisez un redémarrage complet à la place.
::

::note{title="Fichier pid"}
Le bot écrit son pid dans `.glyria/bot.pid` au démarrage. Si le fichier est absent, le bot ne tourne pas (ou a été lancé en dehors de `glyria start`/du point d'entrée build).
::

## Superviseur auto-réparant

`glyria start` exécute le bot build sous un superviseur avec récupération après crash :

| Comportement | Détail |
|---|---|
| Redémarrages avec backoff | Crash → redémarrage après 1s, 2s, 4s, ... (exponentiel) |
| Snapshot stable | Après **60s** d'uptime, le `dist/` courant est snapshoté dans `.glyria/last-good` |
| Rollback en boucle de crash | **3 crashs en 60s** → `dist/` est remplacé par le snapshot last-good et le bot redémarre dessus |
| Abandon | Boucle de crash alors que le build stable est déjà utilisé (ou pas de snapshot) → sortie |

Un mauvais déploiement ne peut donc pas garder votre bot à terre : il revient automatiquement au dernier build ayant tourné de façon stable pendant une minute.

## Changelog de déploiement

Configurez un salon et glyria poste un changelog à chaque déploiement qui modifie les commandes :

```ts
// glyria.config.ts
export default defineGlyriaConfig({
  changelog: {
    channel: "123456789012345678",
  },
})
```

Au démarrage (et au reload), l'ensemble des commandes enregistrées est comparé au snapshot du déploiement précédent (`.glyria/commands.snapshot.json`) et un message stylisé liste les commandes **ajoutées**, **mises à jour** et **supprimées**. Rien n'est posté quand rien n'a changé. Le snapshot est rafraîchi à chaque déploiement dans tous les cas.

## Enregistrement des interactions

glyria peut enregistrer chaque exécution de commande — options, chemin de sous-commande, chaque réponse envoyée, toute erreur — sous forme de fichiers JSON dans `.glyria/interactions/` :

```ts
// glyria.config.ts
export default defineGlyriaConfig({
  recording: true,
})
```

L'enregistrement est **toujours actif en dev** (`glyria dev`) et opt-in en production via `recording: true`.

Les enregistrements alimentent l'outillage time-travel :

```bash
glyria replay <id>   # rejoue une interaction enregistrée contre votre code actuel
glyria bench         # benchmarke les handlers avec des entrées enregistrées
glyria studio        # parcourt les enregistrements dans une interface locale
```

Voir les pages CLI pour [`glyria replay`](/cli/replay), [`glyria bench`](/cli/bench) et [`glyria studio`](/cli/studio).

## Checklist

- `glyria build` puis `glyria start` sous le gestionnaire de processus de votre choix (systemd, Docker, ...).
- Déployez les mises à jour avec `glyria build && glyria reload` — pas de redémarrage, pas d'interruption.
- Gardez le répertoire `.glyria/` accessible en écriture et persistant : il contient le fichier pid, le snapshot last-good, le snapshot des commandes, le store JSON et les enregistrements.
- Définissez `changelog.channel` et `logChannel` pour voir ce que fait votre bot depuis Discord.
