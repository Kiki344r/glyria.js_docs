## Vue d'ensemble

glyria.js embarque un store clé-valeur intégré, disponible sur chaque contexte via `ctx.g.store`. Il est pré-scopé pour que vous n'ayez jamais à construire des préfixes de clés à la main :

```ts
export default new GlyriaCommand()
  .setName("count")
  .setDescription("Count your invocations")
  .execute(async (ctx) => {
    const count = ((await ctx.g.store.user.get<number>("count")) ?? 0) + 1
    await ctx.g.store.user.set("count", count)
    await ctx.g.store.guild.set("lastUser", ctx.user.id)

    await ctx.g.reply.success(`You've run this ${count} time(s).`)
  })
```

## Portées

| Portée | Clé basée sur | Notes |
|---|---|---|
| `ctx.g.store.guild` | Le serveur courant | Lève une erreur en DM |
| `ctx.g.store.user` | L'utilisateur invoquant | |
| `ctx.g.store.global` | Tout le bot | |
| `ctx.g.guildConfig` | Le serveur courant | Namespace séparé pour les réglages par serveur — lève une erreur en DM |

Chaque portée expose la même API asynchrone :

| Méthode | Retourne |
|---|---|
| `get<T>(key)` | `Promise<T \| undefined>` |
| `set(key, value)` | `Promise<void>` |
| `delete(key)` | `Promise<boolean>` |
| `keys()` | `Promise<string[]>` (les clés au sein de la portée) |

`ctx.g.guildConfig` est délibérément séparé de `ctx.g.store.guild` — les réglages d'un côté, les données de l'autre :

```ts
await ctx.g.guildConfig.set("welcomeChannel", channel.id)
await ctx.g.store.guild.set("memberCount", 1024)
```

## En dehors d'un contexte

`useStore()` (auto-importé) vous donne le même store partout — jobs, handlers d'events, setup de modules :

```ts
const store = useStore()

await store.forGuild(guildId).set("raidMode", true)
await store.forUser(userId).get<number>("xp")
await store.global.set("bootedAt", Date.now())
await store.forModule("economy").set("taxRate", 0.05)
await store.forGuildConfig(guildId).get<string>("welcomeChannel")
```

::tip{title="Les modules ont un store scopé gratuitement"}
Dans un [module](/guide/modules), `ctx.store` est déjà scopé à `module:<name>:` — aucun appel `forModule()` nécessaire.
::

## Persistance

L'adapter par défaut est **en mémoire** — les données sont perdues au redémarrage. Passez à l'adapter fichier JSON dans `glyria.config.ts` pour une persistance sans configuration :

```ts
// glyria.config.ts
export default defineGlyriaConfig({
  store: {
    adapter: "json",
    path: ".glyria/store.json", // défaut
  },
})
```

L'adapter JSON garde tout en mémoire et débounce les écritures vers le fichier — bien pour les petits bots.

| Adapter | Persistance | Cas d'usage |
|---|---|---|
| `"memory"` (défaut) | aucune | Dev, caches, tests |
| `"json"` | écritures debouncées vers `.glyria/store.json` | Petits bots |
| `StoreAdapter` personnalisé | à vous de voir | Redis, SQLite, Postgres, ... |

## Adapters personnalisés

Passez n'importe quel objet implémentant `StoreAdapter` comme `adapter`. Les clés arrivent déjà préfixées (`guild:<id>:...`, `user:<id>:...`), donc un backend plat fonctionne :

```ts
// glyria.config.ts
import { createClient } from "redis"
import type { StoreAdapter } from "@glyria/bot"

const redis = createClient()
await redis.connect()

const redisAdapter: StoreAdapter = {
  async get(key) {
    const raw = await redis.get(key)
    return raw === null ? undefined : JSON.parse(raw)
  },
  async set(key, value) {
    await redis.set(key, JSON.stringify(value))
  },
  async delete(key) {
    return (await redis.del(key)) > 0
  },
  async keys(prefix) {
    return redis.keys(`${prefix}*`)
  },
}

export default defineGlyriaConfig({
  store: { adapter: redisAdapter },
})
```

::warning{title="Limites de l'adapter JSON"}
L'adapter fichier JSON charge tout le store en mémoire et réécrit l'intégralité du fichier à chaque changement. Branchez un vrai adapter (Redis, SQLite) pour tout ce qui dépasse les petits bots.
::
