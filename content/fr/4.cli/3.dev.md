## Utilisation

```bash
npm run dev
# ou
npx glyria dev
```

## Ce que ça fait

`glyria dev` démarre votre bot avec le hot reload — aucun redémarrage manuel nécessaire pendant que vous développez.

## Comportement du hot reload

glyria.js surveille vos fichiers et réagit différemment selon ce qui a changé :

| Fichier modifié             | Comportement                                                           |
| --------------------------- | ---------------------------------------------------------------------- |
| `src/commands/**`           | Hot reload des commandes uniquement — pas de redémarrage               |
| `src/events/**`             | Hot reload des événements uniquement — pas de redémarrage              |
| `src/components/**`         | Hot reload des composants uniquement — pas de redémarrage              |
| `src/modules/**`            | Hot-swap des modules — pas de redémarrage                              |
| `glyria.config.ts`          | Hot reload de la config + régénération des types — pas de redémarrage  |
| Fichiers `dev.autoImportDirs` | Régénère les types, puis enchaîne sur la vérification de redémarrage ci-dessous |
| `src/index.ts`              | Régénération des types — pas de redémarrage                            |
| Fichiers `dev.restartPaths` | Redémarrage complet du bot                                             |
| Tout autre fichier `src/**` | Ignoré                                                                 |

Le watcher réagit aux fichiers `.ts` modifiés, créés ou supprimés. Modifier une commande, un événement ou un composant est donc quasi instantané — le bot ne se déconnecte pas de Discord.

::warning{title="Chevauchement des chemins par défaut"}
Par défaut, `autoImportDirs` vaut `["utils", "composables"]` et `restartPaths` vaut `["composables", "utils", "services"]` — modifier un fichier dans `src/utils/` ou `src/composables/` régénère donc les types **et** redémarre complètement le bot. Définissez `dev.restartPaths` vous-même si vous souhaitez une simple régénération des types pour ces dossiers.
::

## Hot-swap des modules

Les changements sous `src/modules/**` hot-swappent le système de modules : les manifestes sont ré-importés, `setup()` s'exécute à nouveau et les hooks sont ré-enregistrés — sans redémarrage.

Si le fichier modifié se trouve dans un dossier `commands/`, `events/` ou `components/` imbriqué dans un module, glyria.js recharge aussi le manager correspondant, de sorte que les handlers imbriqués sont re-routés exactement comme leurs équivalents à la racine de `src/`.

## Enregistrement des interactions

Pendant que `glyria dev` tourne, chaque exécution de commande est automatiquement enregistrée dans `.glyria/interactions/` — le payload, les options, l'utilisateur, les réponses et toute erreur éventuelle.

Vous pouvez ensuite en rejouer n'importe laquelle contre votre code actuel avec [`glyria replay`](/cli/replay). Aucune config nécessaire en dev ; utilisez `recording: true` dans `glyria.config.ts` pour enregistrer aussi en production.

## Génération des types

Dès qu'un fichier de vos dossiers d'auto-import change, glyria.js régénère automatiquement `.glyria/imports.d.ts` pour que votre IDE reste synchronisé sans exécuter `glyria generate` manuellement.

Cela s'exécute aussi quand `glyria.config.ts` change — au cas où vous auriez mis à jour `autoImportDirs`.

## Environnement

`glyria dev` définit automatiquement les variables d'environnement suivantes :

```bash
NODE_ENV=development
GLYRIA_DEV=true
```

`GLYRIA_DEV=true` fait basculer le chargeur de commandes sur les fichiers `src/` et `.ts` directement, au lieu de `dist/` — aucune étape de build nécessaire en dev.

## Anti double-déclenchement

glyria.js utilise [chokidar](https://github.com/paulmillr/chokidar) avec un seuil de stabilité de 200ms par fichier — le watcher attend que le fichier cesse de changer avant de réagir. Cela évite les doubles déclenchements causés par les éditeurs, ESLint ou Prettier qui écrivent le fichier plusieurs fois à la sauvegarde.

## TypeScript

Vos fichiers TypeScript sont exécutés directement via `tsx` — aucune compilation nécessaire pendant le développement. Sauvegardez, glyria.js s'occupe du reste.
