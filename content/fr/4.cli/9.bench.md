## Utilisation

```bash
npx glyria bench <command> [-n 1000] [-c 50] [-o name=value]
```

Exécute un handler de commande de nombreuses fois en parallèle et rapporte les percentiles de latence — un test de charge pour votre bot, sans Discord.

Exécutez `glyria bench` sans argument pour lister toutes les clés de commandes disponibles.

## Flags

| Flag | Défaut | Description |
|---|---|---|
| `-n`, `--runs` | `200` | Nombre total d'exécutions |
| `-c`, `--concurrency` | `20` | Workers parallèles |
| `-o`, `--option` | — | Définit une option de commande, `name=value` (répétable) |

## Clés de commandes

Les sous-commandes utilisent une clé séparée par des deux-points — le même format de clé affiché par `--list` et utilisé par `glyria replay` :

```bash
npx glyria bench ping                                    # /ping
npx glyria bench config:theme:set -o theme=dark          # /config theme set theme:dark
npx glyria bench profile -n 1000 -c 50 -o user=123
```

## Un utilisateur neuf par exécution

Chaque exécution s'effectue avec un tout nouvel utilisateur factice (`bench-user-0`, `bench-user-1`, ...). Les gardes de cooldown par utilisateur ne se déclenchent donc jamais — vos réglages de cooldown ne sérialisent pas le bench et ne faussent pas les chiffres.

## Le rapport

```
  Results
  ────────────────────────────────────────
  total       1243.87ms
  throughput  160.8 runs/s
  min         2.11ms
  avg         5.83ms
  p50         4.92ms
  p95         14.37ms
  p99         28.10ms
  max         41.55ms
```

| Métrique | Signification |
|---|---|
| `total` | Temps réel écoulé pour l'ensemble du bench |
| `throughput` | Exécutions par seconde à la concurrence donnée |
| `min` / `avg` / `max` | Extrêmes et moyenne de latence |
| `p50` / `p95` / `p99` | Percentiles de latence — `p95` est ce que ressentent vos 5% d'utilisateurs les plus lents |

Après le tableau, vous obtenez le nombre d'erreurs : soit `200/200 run(s) completed without errors`, soit le nombre d'exécutions ayant échoué plus la première erreur.

::warning{title="Il mesure VOTRE code, pas Discord"}
Les handlers s'exécutent **in-process contre un faux contexte**. Les chiffres reflètent le code de votre handler — requêtes base de données, calculs, travail attendu — pas la latence de l'API Discord ni ses rate limits. C'est le but : isoler la partie que vous pouvez réellement optimiser.
::
