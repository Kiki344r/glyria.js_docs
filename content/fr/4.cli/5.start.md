## Utilisation

```bash
npm run start
# ou
npx glyria start
```

## Ce que ça fait

`glyria start` lance votre bot compilé en mode production. Il exécute le point d'entrée compilé (`dist/src/index.js`) avec le runtime glyria.js injecté automatiquement — et supervise le processus pour vous.

Ce n'est pas un simple `node dist/src/index.js` : le superviseur redémarre votre bot quand il crashe, détecte les boucles de crash, et peut revenir automatiquement au dernier build connu comme sain.

::warning{title="Build requis"}
`glyria start` nécessite un build compilé. Si `dist/src/index.js` est introuvable, il se termine avec une erreur.

Exécutez toujours `glyria build` avant `glyria start`.
::

## Workflow de production

```bash
# 1. compiler
npm run build

# 2. démarrer
npm run start
```

## Superviseur auto-réparant

Quand votre bot se termine avec un code non nul (une sortie propre ou un `SIGTERM` ne déclenche jamais de redémarrage), le superviseur entre en action :

**Backoff exponentiel.** Chaque crash redémarre le bot après un délai croissant — 1s après le premier crash, puis 2s. Un troisième crash dans la fenêtre déclenche le rollback de boucle de crash ci-dessous, donc des délais plus longs ne se produisent jamais. Le compteur ne regarde que les crashs des 60 dernières secondes, donc un crash occasionnel survenu longtemps après le précédent redémarre rapidement.

**Détection des boucles de crash.** 3 crashs en 60 secondes sont considérés comme une boucle de crash — redémarrer le même build ne servira à rien, donc le superviseur effectue un rollback à la place.

## Snapshots stables

Une exécution qui tient 60 secondes est considérée comme stable. Quand cela arrive, le superviseur :

1. Réinitialise le compteur de crashs
2. Snapshot `dist/` vers `.glyria/last-good`

Ce snapshot devient la cible du rollback — toujours le dernier build qui a réellement survécu en production.

## Comment fonctionne le rollback

Quand une boucle de crash est détectée :

1. `dist/` est supprimé et remplacé par le snapshot `.glyria/last-good`
2. Le bot redémarre sur ce dernier build stable
3. Si le build restauré tient 60 secondes, il devient le nouveau snapshot stable

S'il n'y a pas encore de snapshot, ou si le bot boucle en crash **à nouveau après un rollback déjà effectué**, le superviseur abandonne proprement et se termine avec le code 1 — il ne boucle jamais indéfiniment sur un build cassé.

::tip{title="Un déploiement raté ? Vous êtes couvert"}
`glyria build && glyria start` avec une release cassée signifie : 3 crashs, rollback automatique, et vos utilisateurs sont de retour sur la version précédente — avant même que vous ayez lu la stack trace.
::

## Arrêt

`Ctrl+C` (`SIGINT`) et `SIGTERM` sont transmis au processus du bot, et le superviseur ne le redémarre pas — arrêter le bot volontairement est toujours propre.

## Différence avec le mode dev

| | `glyria dev` | `glyria start` |
|---|---|---|
| Source | `src/` (TypeScript) | `dist/` (JavaScript) |
| Hot reload | ✅ | ❌ (utilisez [`glyria reload`](/cli/reload)) |
| Build requis | ❌ | ✅ |
| Redémarrages auto-réparants | ❌ | ✅ |
| Cas d'usage | Développement | Production |
