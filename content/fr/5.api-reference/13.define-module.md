## Vue d'ensemble

`defineModule` déclare un module de fonctionnalité autonome — son schéma de config, ses hooks de cycle de vie et son API publique. Les modules vivent dans `src/modules/<name>/index.ts` (ou `src/modules/<name>.ts`), ou sont installés comme packages npm listés dans la [clé de config `modules`](/api-reference/define-glyria-config#modules).

```ts
// src/modules/economy/index.ts
export default defineModule({
  name: "economy",
  version: "1.0.0",
  description: "Balances and daily rewards",
  defaultConfig: { startingBalance: 100 },

  setup(ctx) {
    // objet retourné = l'API publique du module
    return {
      async addBalance(userId: string, amount: number) {
        const current = (await ctx.store.get<number>(`bal:${userId}`)) ?? 0
        await ctx.store.set(`bal:${userId}`, current + amount)
      },
    }
  },

  hooks: {
    onReady(ctx) {
      ctx.logger.info("economy ready")
    },
  },
})
```

::tip{title="Importation automatique"}
`defineModule`, `defineCommand`, `defineEvent` et `defineHook` sont disponibles globalement — aucun import n'est nécessaire.
::

## ModuleDefinition

| Clé             | Type                              | Requis   | Description                                                              |
| --------------- | --------------------------------- | -------- | ------------------------------------------------------------------------ |
| `name`          | `string`                          | ✅       | Nom unique du module (`defineModule` lève une exception sans lui)         |
| `version`       | `string`                          | —        | Version informative, affichée par `glyria module list`                    |
| `description`   | `string`                          | —        | Description informative                                                   |
| `dependsOn`     | `string[]`                        | —        | Noms des modules qui doivent être chargés avant celui-ci                  |
| `config`        | `ConfigSchema<C>`                 | —        | Valide l'entrée du module dans `moduleConfig` (les schémas zod fonctionnent tels quels) |
| `defaultConfig` | `unknown`                         | —        | Utilisé quand `moduleConfig` n'a pas d'entrée pour ce module              |
| `setup(ctx)`    | `(ctx: ModuleContext<C>) => unknown` | —     | Point d'entrée — sa valeur de retour est l'**API publique** du module, consommable via `ctx.modules.get(name)` |
| `hooks`         | `ModuleHooks<C>`                  | —        | Hooks de cycle de vie et de commandes                                     |

### `config` — validation par schéma

`ConfigSchema<C>` est compatible zod — tout ce qui possède une méthode `.parse()`, ou une simple fonction de validation :

```ts
type ConfigSchema<C> = { parse(input: unknown): C } | ((input: unknown) => C)
```

```ts
import { z } from "zod"

export default defineModule({
  name: "economy",
  config: z.object({
    startingBalance: z.number().default(100),
    currency: z.string().default("🪙"),
  }),
  setup(ctx) {
    ctx.config.startingBalance // number typé
  },
})
```

L'entrée brute est `moduleConfig[name]` de `glyria.config.ts`, avec repli sur `defaultConfig`. Un schéma qui lève une exception désactive le module (statut `invalid config`) sans faire tomber le bot.

## ModuleContext

Passé à `setup()` et à chaque hook de cycle de vie.

| Membre    | Type                   | Description                                                            |
| --------- | ---------------------- | ----------------------------------------------------------------------- |
| `name`    | `string`               | Le nom du module                                                        |
| `client`  | `GlyriaClient`         | Le client du bot                                                        |
| `config`  | `C`                    | Config validée pour ce module (depuis `moduleConfig`)                   |
| `store`   | `ScopedStore`          | Store scopé à ce module (préfixe `module:<name>:`)                      |
| `logger`  | `ModuleLogger`         | `info`/`warn`/`error`, taggé `mod:<name>` dans la console               |
| `modules` | `ModuleRegistryAccess` | Accès aux API publiques des autres modules : `get(name)` (lève une exception quand la cible n'est pas chargée ou inactive) et `has(name)` |

```ts
setup(ctx) {
  const economy = ctx.modules.get("economy") // typé via l'augmentation GlyriaModules
  ctx.logger.info(`loaded, depends on economy: ${ctx.modules.has("economy")}`)
}
```

## ModuleHooks

Tous les hooks peuvent être asynchrones. Chaque hook est enveloppé dans un try/catch par le manager — un hook qui crashe est loggé, signalé à `onError` et comptabilisé (voir les [règles d'isolation](#règles-disolation)).

| Hook                                | Signature                                                               | Se déclenche                                              |
| ----------------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------- |
| `onLoad`                            | `(ctx: ModuleContext<C>) => unknown`                                      | Avant `setup()`, au chargement du module                   |
| `onReady`                           | `(ctx: ModuleContext<C>) => unknown`                                      | Quand le bot est prêt                                      |
| `onUnload`                          | `(ctx: ModuleContext<C>) => unknown`                                      | Avant hot reload / hot-swap / arrêt                        |
| `onError`                           | `(ctx: ModuleContext<C>, error: unknown) => unknown`                      | Quand le module (ou l'un de ses hooks) lève une exception  |
| `onGuildJoin`                       | `(ctx: ModuleContext<C>, guild) => unknown`                               | Sur `guildCreate`                                          |
| `onGuildLeave`                      | `(ctx: ModuleContext<C>, guild) => unknown`                               | Sur `guildDelete`                                          |
| `beforeCommand`                     | `(ctx: GlyriaContext, meta: CommandRunMeta, next: () => Promise<void>) => unknown` | Middleware global — avant **chaque** commande. Sautez `next()` pour annuler |
| `afterCommand`                      | `(ctx: GlyriaContext, meta: CommandRunMeta, result: unknown) => unknown`  | Après la fin de chaque handler de commande                 |
| `onCommandRun`                      | `(ctx: GlyriaContext, meta: CommandRunMeta) => unknown`                   | Notification quand une commande s'exécute                  |

### CommandRunMeta

| Champ  | Type                              | Description                                          |
| ------ | --------------------------------- | ---------------------------------------------------- |
| `name` | `string`                          | Clé de commande entièrement résolue, ex. `"config:theme:set"` |
| `kind` | `"chat" \| "user" \| "message"`   | Quelle surface de commande a été invoquée            |

### Middleware `beforeCommand`

Les hooks `beforeCommand` de tous les modules actifs forment une chaîne à la Koa. Appelez `next()` pour laisser le pipeline continuer ; ne pas l'appeler annule la commande silencieusement (votre hook est censé avoir déjà répondu). Un middleware qui lève une exception ne bloque **pas** les autres commandes — la chaîne continue au-delà.

```ts
hooks: {
  async beforeCommand(ctx, meta, next) {
    const banned = await ctx.g.store.user.get<boolean>("blacklisted")
    if (banned) {
      await ctx.g.reply.error("You are blacklisted.").ephemeral()
      return // pas de next() → commande annulée
    }
    await next()
  },
}
```

## Helpers du SDK

Des points d'entrée fins et typés pour les auteurs de modules — les mêmes constructeurs, une intention plus stricte :

| Helper                   | Retourne         | Description                                          |
| ------------------------ | ---------------- | ---------------------------------------------------- |
| `defineCommand(fn)`      | `GlyriaCommand`  | `fn` reçoit une `GlyriaCommand` neuve                |
| `defineEvent(fn)`        | `GlyriaEvent`    | `fn` reçoit un `GlyriaEvent` neuf                    |
| `defineHook(hooks)`      | `ModuleHooks<C>` | Helper identité pour typer un objet de hooks autonome |

```ts
// src/modules/economy/commands/balance.ts
export default defineCommand((cmd) =>
  cmd
    .setName("balance")
    .setDescription("Show your balance")
    .execute(async (ctx) => {
      const bal = (await ctx.g.store.user.get<number>("balance")) ?? 0
      await ctx.g.reply.primary(`You have ${bal} 🪙`)
    }),
)
```

## API inter-modules typées

Augmentez l'interface `GlyriaModules` pour que `ctx.modules.get(name)` retourne une API typée :

```ts
declare module "@glyria/bot" {
  interface GlyriaModules {
    economy: { addBalance(userId: string, amount: number): Promise<void> }
  }
}

// ailleurs, dans un autre module :
const economy = ctx.modules.get("economy")
await economy.addBalance(userId, 50) // entièrement typé
```

## ModuleManager

Le framework instancie un seul `ModuleManager` ; vous interagissez avec lui principalement via le CLI (`glyria module list`, `glyria module reload <name>`). Méthodes publiques :

| Méthode                         | Retourne           | Description                                                        |
| ------------------------------- | ------------------ | ------------------------------------------------------------------- |
| `register(definition, source?)` | `boolean`          | Met en file une définition de module (`false` quand la valeur n'est pas un résultat de `defineModule`) |
| `loadAll(moduleConfig?)`        | `Promise<void>`    | Tri topologique par `dependsOn`, puis chargement de chaque module (validation de config → `onLoad` → `setup`) |
| `reload(name, moduleConfig?)`   | `Promise<boolean>` | Hot-swap d'un seul module en place — `onUnload`, ré-import depuis sa source, rechargement. Les autres restent intacts |
| `hotReload(moduleConfig?)`      | `Promise<void>`    | Décharge tout, redécouvre depuis le disque, recharge tout           |
| `list()`                        | `{ name, version?, status, reason?, hooks }[]` | Snapshot d'introspection de chaque module |
| `getApi(name)`                  | `unknown`          | L'API publique retournée par le `setup()` d'un module               |

### Ordre de chargement

`dependsOn` pilote un tri topologique. Un module échoue au chargement (statut `error`) quand :

- une dépendance est manquante — `missing dependency "<dep>"`
- une dépendance a elle-même échoué — `dependency "<dep>" failed to load`
- un cycle de dépendances existe — `dependency cycle: a → b → a`

### Règles d'isolation

Un module qui crashe ne doit jamais faire tomber le bot :

- Les échecs de validation de config, d'`onLoad` et de `setup` désactivent **ce module uniquement** (statut `error`, raison `invalid config` / `setup crashed`).
- Chaque hook d'exécution tourne dans un try/catch ; une erreur est loggée, transmise au hook `onError` du module (qui a lui-même le droit d'échouer silencieusement) et comptabilisée.
- Après **5** erreurs de hooks sur la durée de vie du module (le compteur est cumulatif et ne se réinitialise jamais), le module est auto-désactivé (statut `disabled`, raison `auto-disabled after 5 hook errors`).
- Un middleware `beforeCommand` qui lève une exception ne bloque pas le pipeline — la chaîne continue avec le module suivant.

### ModuleStatus

| Statut     | Signification                                                    |
| ---------- | ----------------------------------------------------------------- |
| `active`   | Chargé et en marche — les hooks se déclenchent, l'API est disponible |
| `disabled` | Auto-désactivé après trop d'erreurs de hooks                       |
| `error`    | Échec au chargement (config invalide, setup crashé, problème de dépendance) |
